# Data Model and State Ownership

All recognition runtime entities are session-local and non-persistent. JSON wire fields use camelCase;
C++ type names use PascalCase. Offline DatasetManifest/ModelManifest/EvaluationRun are separate
research artifacts and never populated from ordinary demo sessions.
Process-wide aggregate metrics are separately defined in [telemetry.md](contracts/telemetry.md),
with no session identifiers/content. Offline model candidates and release manifests follow
[model-promotion.md](contracts/model-promotion.md); neither stores ordinary demo media.

## Session state machine

`created -> awaitingInput -> processing -> reviewing -> ending -> ended`.

- Creation atomically acquires the one-session lease. A conflicting create returns busy and
  does not reveal the active session ID, cookie or results.
- SSE attachment within 10 seconds moves created to awaitingInput and emits ready.
- Valid camera frames or a completed validated upload begin processing. Camera stays processing;
  image completion and video EOF enter reviewing. Finishing source input does not erase results.
- Video seek from processing/reviewing increments epoch, stops old playback/work, clears tracks
  and history, retains the uploaded source file, and returns to processing at the requested time.
- Source replacement is DELETE old session followed by POST new session; no inherited identities.
- Stop, event-stream loss, lease expiry, malformed decoder failure or unrecoverable inference
  failure enters ending. Invalidate publication first, cancel pending work, close handles, erase
  buffers/history/cookies and unlink tmpfs files; release the lease after worker-owned resources
  are safely cleaned. Return busy during cleanup. A new session cannot reuse the old resources.
- Recoverable rejected uploads leave awaitingInput, remove partial files and release admission.
  They allow another attempt within the configurable budget; only one successfully accepted file
  consumes the session source slot. At budget exhaustion offer explicit end/start recovery, not
  automatic retries. Counters and MAX_UPLOAD_ATTEMPTS semantics are defined in contracts/api.md. Image/video decoding
  failure after work begins ends the session with an accessible error; restarting is explicit.
- UploadReceipt transitions idle -> receiving -> validating -> accepted/rejected, or receiving ->
  aborted/rejected. Each transition advances stateRevision and emits upload.state even without a
  lifecycle change. A subsequent explicit admitted attempt replaces a rejected/aborted receipt.
  GET upload-status builds an atomic snapshot from the receipt and session counters/flags; unknown
  transfer outcomes require reconciliation or explicit end/start, never speculative body resubmission.
- Heartbeat deadline uses server monotonic time. Client closes EventSource on error, stops tracks,
  aborts HTTP and audio locally, clears state, and never automatically reconnects.

## Tracking and consensus

`tentative -> confirmed -> lost -> removed`. Confirmation requires the research.md consensus;
accepted still-image observations create confirmed one-image tracks directly. Lost tracks may
reassociate within 2 source seconds. Removed tracks are erased, while only bounded announcement
history remains. A new encounter receives a new ID. Tracking updates use actual elapsed source
time in motion prediction and expiry, not an assumed constant camera FPS.

When a confirmed category first becomes available, announce its meaning. Text-bearing categories
may produce a later revision when text first stabilizes; that is new information, not a duplicate.
Changing accepted text requires two matching new observations, not one transient OCR alternative.
Nonaccepted conflicting readings do not overwrite established text. A lost/removed track invalidates
unoffered pending announcements; reacquisition may enqueue an unspoken accepted revision again if
it is currently relevant. Entries already started remain suppressed for that track/revision.

## Announcement state machine

`pending -> synthesizing -> offered -> playing -> completed` with terminal `cancelled`, `expired`,
`dropped`, or `failed` from appropriate states. Synthesis may only start while the playback slot is
free. The offered artifact counts as occupying that slot. Signature suppression checks pending, synthesizing,
offered and started entries; only a client started acknowledgment marks information as spoken.
Automatic announcements copy scalar track/revision/frame/capture metadata from AcceptedInformation
at enqueue time, retaining no frame pixels. Manual repeat/recovery copies only the retained text
into a new announcement with null trackId/revision/frameId and no capture timestamp; source entities
need not remain alive. A manual started acknowledgment updates replay history/last-started text but
never marks an automatic track/revision signature spoken or contributes to capture latency metrics.

- No higher-priority arrival preempts speech already playing. It affects selection of the next item.
- Expire pending/offered automatic items after 5 seconds; skip native synthesis results that arrive
  after expiry, epoch change, mute or end. If a track/revision becomes obsolete before playback,
  send audio.cancel and require client validation of generation before starting.
- Mute increments audioGeneration, clears pending/offered artifacts and immediately stops local
  speech. Recognition continues while muted, but creates no automatic pending backlog. Unmute
  enables new accepted revisions/encounters only. Manual repeat can play the last started text.
- Repeats respect mute, use a new announcement ID and isReplay=true, take the next available slot,
  and do not alter automatic duplicate counts. Coalesce repeated clicks to one pending replay.
- Failure to activate audio blocks automatic dispatch until Enable audio or an explicit recover
  action succeeds. Failed items are not automatically retried. Read latest result targets the
  separate latestAcceptedDescription even when no audio has ever started; repeat still targets
  the last started text. Both are intentional playback and respect mute. A missing started/ended acknowledgment times out
  at the offered expiry or declared audio duration +5 seconds. On timeout, cancel/fence that
  generation and require a matching CancellationReceipt acknowledgment before offering another item. If that
  acknowledgment does not arrive within 5 seconds, end the session; never assume silence.
- Playback results must match session/epoch/generation/announcement; stale results cannot revive
  cancelled content. Cancellation acknowledgments instead match cancellationId and its generation
  cutoff against the session receipt, without the current-epoch/generation test. One pending receipt
  and the latest acknowledged receipt support supersession/idempotency; follow contracts/api.md.

## Memory, isolation and validation

Session executor owns mutable state; vision and speech workers receive immutable owning inputs.
Callbacks return values through public interfaces, then check the current epoch/generation before
publishing. Cancellation is cooperative; a native call need not be forcibly interrupted to prevent
stale output. RAII owns Mat buffers, ORT handles, Tesseract UTF-8 allocations, decoder resources and
speech callback buffers. Do not detach threads referencing destroyed sessions.

HTTP body limits and decoded pixel/codec limits are checked before expensive work. Audio URLs are
session-owned capabilities requiring the same cookie; no transcript, token or filename in logs.
Errors use fixed public codes and safe messages, not exception dumps. Research persistence requires
explicit offline commands and authorised input paths; the online server cannot write research-data
or reports mounts. Server startup clears any stale tmpfs request spools before accepting sessions.

## Explicit recovery and retention

LatestAcceptedDescription is independent of HistoryEntry and of the last-started text. An accepted
image result therefore remains readable after initial autoplay rejection. A user recover action
uses its descriptionId, creates origin=recovery/isReplay=true and queues only that description;
unknown/stale IDs are rejected. At most one pending manual action per description is kept.
It has no automatic freshness/track-presence requirement, because it is deliberate historical
review, but session/epoch/mute ownership still applies. Clear it on seek/end/replacement.
This exemption concerns the retained description: each newly offered manual WAV still has a
five-second fetch/start lifetime, the same duration+5-second completion timeout and cancellation
barrier as other offers. Synthesis for a coalesced manual intent begins only when its slot/barrier
permits; do not retain frames or track objects just to populate historical audio.ready fields.

maxUploadAttempts snapshots the validated server setting, default3; 0 is unlimited. Pre-body admission
increments uploadAttemptsUsed only for a granted request. Failed/rejected/aborted admitted transfers
consume an attempt, never the successful-source slot. Mark hasAcceptedUpload only after full upload
validation commits the file. No later /media may replace that accepted source in the same session.
